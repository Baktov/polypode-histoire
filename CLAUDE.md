# CLAUDE.md — Polypode Histoire (Addon WoW)

Conventions communes et procédure de documentation de tous les modules Polypode (chargées
automatiquement, quel que soit le dossier ouvert) :

@../Polypode/MODULES.md

Addon compagnon de **Polypode** (dossier voisin `../Polypode`, dépôt séparé) : **journal
chronologique commun** des événements importants de tous les personnages joués. Rester **simple** :
on n'ajoute un type d'événement que s'il raconte l'histoire des personnages, sans détail superflu.

## Architecture

| Fichier | Rôle |
|---|---|
| `Polypode_Histoire.toc` | `## Dependencies: Polypode`, SavedVariables par personnage `PolypodeHistoireChar` (`rep[factionID]` = rang connu ; `friends`, `bnet` = `{ [nom] = true }`, `guild` = nom ou "", `clubs` = `{ [id] = { name, b } }` ; écrit par le seul client du personnage), de compte `PolypodeHistoireData` (le journal) et `PolypodeHistoireDB` (fenêtre : `open` repli, `showPatches` case « Ext » (nil = vrai), `filters` = `{ [catégorie] = true }`, `width` / `height`) |
| `Journal.lua` | Relevé, stockage, synchro, export. Événement = texte `heure~nom-royaume~type~champs...` (`GetServerTime`, champs nettoyés par `Clean` : ni `~`, ni `\|`, ni saut de ligne), rangé dans `store.days["AAAA-MM-JJ"]` (jour local, `DayOf`) trié par heure (`Insert`, doublons par l'index `seen` ; refusé si antérieur à `store.cutoff`). `Record(type, ...)` : événement du personnage joué, ajouté puis envoyé (`Send("E")`) et gardé dans `sessionEvents`. Types : `in` (`PLAYER_ENTERING_WORLD` isLogin → `OnLogin` : si le dernier événement du personnage est un `out` de moins de `SHORT_DELAY` = 180 s, ce `out` est retiré et rien n'est noté ; sinon `loginEvent` / `loginTime`), `out` (`OnLogout` depuis les accroches `Logout` / `Quit` / `ForceQuit`, sinon à `PLAYER_LOGOUT` hors `/reload` — accroches `ReloadUI` / `C_UI.Reload` ; si `loginEvent` date de moins de `SHORT_DELAY`, il est retiré et rien n'est noté, `loggedOut = "short"` ; `CancelLogout` retire le `out` ou remet la connexion). Retraits par `Withdraw` : `Remove` + `Send("R")` ; suppressions à la main par `ns.Delete(événements)` : `Remove` + `Send("D")` ; les deux gardés dans `withdrawn[événement] = "R" / "D"` et renvoyés par `OnPeer`, `grp` équipe~membres (`CheckTeams` 2 s après `GROUP_ROSTER_UPDATE` : équipes dont le joueur est leader, tous les membres trouvés par `P.FindGroupUnit` ; seul le passage à « au complet » est noté, état initial relevé en silence à chaque `PLAYER_ENTERING_WORLD`), `lvl` (`PLAYER_LEVEL_UP`), `ach` id (`ACHIEVEMENT_EARNED`, pas si `alreadyEarned`), `ilvl` nouveau~ancien (`CheckItemLevel` 3 s après `PLAYER_EQUIPMENT_CHANGED` / `PLAYER_AVG_ITEM_LEVEL_UPDATE` : `GetAverageItemLevel` équipé arrondi par défaut, noté s'il dépasse `store.ilvl[clé]`, première lecture = référence), `enter` nom~difficulté~genre (`UpdateVisit` à chaque `PLAYER_ENTERING_WORLD` : `CurrentInstance` = gouffre — difficulté 208 ou `HasActiveDelve` —, donjon « party » ou raid, identifiant `instanceID-difficulté` ; session `visit = { id, name, start, last }` ; pas d'entrée au `/reload` (`RestoreVisit` : début et dernière fin retrouvés dans le journal) ni en revenant moins de `REENTRY_DELAY` = 900 s après en être sorti (`left` / `leftAt`)) ; durée en dernier champ des fins d'instance (`Elapsed` : depuis `visit.last` ou `visit.start`, puis `visit.last` = maintenant ; `mplus` : `info.time` du chrono en ms), `delve` nom~palier~section~durée (`SCENARIO_COMPLETED` dans un gouffre, `InDelve` : `C_DelvesUI.HasActiveDelve` ou difficulté 208 ; `ReadDelveState` : palier = chiffres du `tierText` du widget `ScenarioHeaderDelves` de l'étape (`C_ScenarioInfo.GetScenarioStepInfo().widgetSetID` → `C_UIWidgetManager.GetAllWidgetsBySetID`), repli `C_DelvesUI.GetActiveDelveTier().tier` s'il est > 0 (données du groupe à l'entrée : 0 en solo, d'où « 0 » dans les anciens événements, non affiché) ; section = titre de l'étape ; relevé gardé dans `delveState` par `UpdateDelveState` à `SCENARIO_UPDATE` / `SCENARIO_CRITERIA_UPDATE` / `PLAYER_ENTERING_WORLD`, l'étape pouvant être passée à `SCENARIO_COMPLETED` ; valeurs secrètes écartées par `SafeText`), `dng` nom~difficulté~durée (`ENCOUNTER_END` réussi en instance « party » hors clé, si le boss est le dernier du Journal des donjons : `IsLastDungeonBoss`, `EJ_GetInstanceForMap` + `EJ_GetEncounterInfoByIndex` 7e retour), `mplus` nom~niveau~àTemps~améliorations~durée (`CHALLENGE_MODE_COMPLETED` → `C_ChallengeMode.GetChallengeCompletionInfo`, pas les `practiceRun`), `toy` / `mount` / `pet` id~nom (`NEW_TOY_ADDED` → `C_ToyBox.GetToyInfo`, `NEW_MOUNT_ADDED` → `C_MountJournal.GetMountInfoByID`, `NEW_PET_ADDED` → `C_PetJournal.GetPetInfoByPetID` : speciesID et nom ; nom manquant relu à l'affichage par `CollectionName`), `renown` id~palier~faction (`MAJOR_FACTION_RENOWN_LEVEL_CHANGED`, en montant), `rep` id~rang~faction~niveau (`FACTION_STANDING_CHANGED` → `ReputationRank` : amitié `C_GossipInfo.GetFriendshipReputation` / `GetFriendshipReputationRanks().currentLevel`, sinon `reaction` 1..8 et `FACTION_STANDING_LABEL<n>` ; factions majeures écartées ; noté si le rang dépasse `PolypodeHistoireChar.rep[id]`, première lecture = référence ; références posées 5 s après la connexion par `SeedReputations` pour les factions visibles), `friend` nom~+/-~c/b, `guild` nom~+/-, `club` nom~+/-~c/b (`CheckSocial`, 2 s après `FRIENDLIST_UPDATE` / `BN_FRIEND_LIST_SIZE_CHANGED` / `PLAYER_GUILD_UPDATE` / `CLUB_ADDED` / `CLUB_REMOVED` (`ScheduleSocial`), et `SOCIAL_DELAY` = 10 s après la connexion (`socialReady`) : `ReadFriends` (`C_FriendList`), `ReadBNetFriends` (`C_BattleNet.GetFriendAccountInfo().battleTag` sans `#n`), `ReadGuild` (`IsInGuild` / `GetGuildInfo`, nil si nom pas encore connu), `ReadClubs` (`C_Club.GetSubscribedClubs`, guilde exclue) comparés par `DiffSets` à `PolypodeHistoireChar` ; `Usable` : liste vidée d'un coup = pas chargée, ignorée ; Battle.net affiché sans nom de personnage), `boss` nom~difficulté~raid~durée (`ENCOUNTER_END` réussi en raid ; valeurs secrètes écartées par `issecretvalue`). Synchro : `HIST:token:E:<événement>` (ajout), `R` (retrait, seulement de son personnage), `D` (suppression à la main, de n'importe quel client de l'équipe ; gardée aussi dans `withdrawn` pour être renvoyée), `P:<AAAA-MM-JJ>` (purge après export → `ApplyCutoff`) ; un événement reçu n'est accepté que de son personnage (`P.IsSender`) ; à chaque HELLO/HI (`OnPeer`), les `SESSION_RESEND_MAX` derniers `sessionEvents` sont renvoyés, puis les retraits `withdrawn`. Taille estimée `size` (texte + `LINE_OVERHEAD` par événement + `DAY_OVERHEAD` par jour, `Reindex`) ; seuils `ns.WARN_SIZE` 2 Mo (message 10 s après la connexion) et `ns.ALERT_SIZE` 5 Mo. Export `ns.Export` : jours antérieurs à `KeepFrom()` (1er du mois précédent) fusionnés sans doublon dans `PolypodeHistoireArchive.days` après `C_AddOns.LoadAddOn("Polypode_Histoire_Archive")`, puis `ApplyCutoff` et `Send("P")` |
| `Histoire.lua` | Fenêtre `PolypodeHistoireFrame` (`P.ToggleHistoire`, `ns.Refresh` = `P.RefreshHistoire`, `P.ui.histoireFrame`), redimensionnable (`MIN_WIDTH` 500) ; barre de titre : cases de filtre `FILTERS` à gauche (connexions, hauts faits, gouffres, donjons, raids, collections, renom et réputation, social) (libellé abrégé `short`, `label` en infobulle) (`frame.filterChecks`, `PolypodeHistoireDB.filters`, aucune cochée = tout), titre à droite, puis case « Ext » `frame.patchCheck` (`showPatches`) contre la croix ; `IsOpen` : période en cours ou à venir dépliée par défaut ; `BuildItems` (jours filtrés par `Filtered` → `EventCategory` : `CATEGORY_OF_KIND`, entrée `enter` selon son genre `CATEGORY_OF_ENTRY` ; jours vides omis, totaux sur les événements retenus ; jours de `PATCHES` — sorties de patchs Retail, date européenne, **à compléter à chaque patch** — ajoutés dans les mois affichés et, à venir, toujours (« (à venir) ») si `showPatches`, nom en vert `PATCH_COLOR` dans l'en-tête du jour, `item.patch`, `IS_RETAIL`) → en-têtes `{ header = 1..3 (année, mois, jour), key, label, count }` du plus récent au plus ancien, dépliés selon `IsOpen` (`PolypodeHistoireDB.open[clé]`, sinon déplié pour la période en cours) ; lignes d'un jour par `DayLines`, renvoyées du plus récent au plus ancien (même type et mêmes champs, durée exceptée — `DURATION_FIELD` —, personnages différents, moins de `MERGE_WINDOW` = 300 s d'écart → une ligne, sauf `grp`), texte `EventText` (noms à la couleur de classe, verbe au pluriel, noms de hauts faits — `select(2, GetAchievementInfo(id))` — et de difficultés lus au moment de l'affichage ; « out » suivi du temps joué `DurationText` si un seul personnage), temps joué `SessionDurations` (calculé à l'affichage sur tout le journal : « out » − dernier « in » du même personnage ; `line.durations`, aussi dans l'infobulle), clic sur un haut fait → `OpenAchievement` (`ShowAchievementFrameForAchievement`, repli `AchievementFrame_LoadUI` + `AchievementFrame_SelectAchievement`), infobulle `ItemTooltip` (heure de chaque personnage, « Clic droit : supprimer »). Chaque ligne garde ses textes d'événements (`line.events`) ; clic droit (`OnItemClick`) → `AskDelete` → popup `POLYPODE_HISTOIRE_DELETE` (données = `line.events`) → `ns.Delete`. En-tête `HeaderText` (événements, taille, couleur selon les seuils), boutons « Tout replier » / « Tout déplier » et « Exporter » (`AskExport` → popup `POLYPODE_HISTOIRE_EXPORT`). Bouton `P.AddTitleButton` « Histoire » (`P.ui.histoireButton`), commande `/poly histoire` |
| `Polypode_Histoire_Archive/` | Addon **chargé à la demande** (`## LoadOnDemand: 1`, dépend de Polypode_Histoire), SavedVariables `PolypodeHistoireArchive` (`format`, `updated`, `days` au même format que le journal) : jamais lu au lancement, donc jamais réécrit par les autres clients ; relié au jeu par sa **propre jonction** (`Interface\AddOns\Polypode_Histoire_Archive` → ce sous-dossier ; WoW ne lit pas les dossiers imbriqués) |

**Fichier partagé** : les comptes de multibox partagent le dossier `SavedVariables` (jonctions de
`WTF\Account`) ; le dernier client qui quitte écrit `Polypode_Histoire.lua`. D'où la synchro de
chaque événement, le renvoi de la session aux clients qui arrivent, et la purge diffusée à l'export.

## Dépendances vers Polypode (API publique utilisée)

`P.AddTitleButton`, `P.RegisterSlashCommand`, `P.RegisterMessageHandler`, `P.RegisterPeerCallback`,
`P.WhisperOnline`, `P.IsSender`, `P.MAX_MESSAGE_LENGTH`, `P.GetTeamToken`, `P.GetCharKey`,
`P.GetDisplayName`, `P.db.roster`, `P.GetTeams`, `P.GetTeamMembers`, `P.GetTeamLeader`,
`P.FindGroupUnit`, `P.CreatePanel`, `P.CreateScrollList`, `P.SetListData`, `P.SkinFrame`,
`P.SkinPanel`, `P.SkinButton`, `P.ShowTooltip`, `P.ui`. Toute évolution de ces fonctions dans
Polypode doit rester compatible, ou ce fichier doit suivre.

## Pistes

- Détail dépliable d'un événement (butin d'un gouffre ou d'un donjon) : à vérifier d'abord, les
  messages de butin pouvant être des valeurs secrètes en instance sur Midnight.
- Logiciel tiers lisant `Polypode_Histoire_Archive.lua` (conversion JSON / CSV, publication).

## Après chaque modification

Appliquer la procédure de `../Polypode/MODULES.md` (« Après chaque modification d'un module »),
sans attendre qu'on le demande : version du `.toc` et du commit, ligne en tête de la section
« Version » du `README.md` et sections d'utilisation, ce fichier (architecture, dépendances),
Polypode si le périmètre change, puis commit et push sur `origin` (https://github.com/Baktov/polypode-histoire).
